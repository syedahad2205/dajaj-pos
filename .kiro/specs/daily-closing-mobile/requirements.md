# Requirements Document

## Introduction

This document defines the requirements for **DAJAJ Daily Closing Mobile** — a React Native (Android + iOS) client that ports the existing web Daily Closing module to mobile. This is not a redesign, not a new finance system, and not a new backend. The mobile app is a second client against the same Firestore collections and the same business logic that already powers `app/admin/finance/closing/page.tsx` and `services/financeClosingService.ts`.

The web implementation is the specification. Every formula, validation rule, and locking behavior below is transcribed directly from the existing code, not re-derived. Where the mobile app requires new infrastructure (mobile authentication, offline queueing), that infrastructure is designed to sit *around* the existing service layer, never to duplicate or reimplement it.

This feature introduces:
- A mobile-specific authentication bridge (Finance User credentials → Firebase Custom Token).
- A new `isFinanceUser()` Firestore rules helper, scoped tightly to the collections Daily Closing needs.
- A small set of new "identity-forwarding" API routes that re-verify the caller's Firebase ID token server-side and then call the *existing, unmodified* `financeClosingService.ts` functions — so the transactional posting/locking logic is never duplicated in the client or in Firestore rules.
- The React Native app itself: Splash, Login, Home, Daily Closing, History, Settings.

## Glossary

- **Finance User**: A record in the `finance_auth` Firestore collection (see `lib/finance.ts` `FinanceUser`). Has no Firebase Auth account of its own prior to this feature. Identified by a unique lowercase `username` and a bcrypt `passwordHash`. Never an Admin.
- **Admin**: An existing Firebase Auth user with a corresponding `/admins/{uid}` document. Unrelated to Finance Users. Continues to use the web app exactly as today.
- **Custom Claim**: A key/value pair embedded in a Firebase Auth ID token, set via the Admin SDK's `createCustomToken(uid, claims)` and later readable in Firestore Security Rules as `request.auth.token.<key>`.
- **Custom Token**: A short-lived signed token minted by the Firebase Admin SDK, exchanged by the client for a real Firebase Auth session via `signInWithCustomToken()`.
- **Daily Closing / Closing Day**: One document in `fin_daily_closing/{date}` (`FinanceDailyClosing`), keyed by `YYYY-MM-DD`. Represents a single business day's cash register reconciliation.
- **Locked Day**: A Daily Closing document where `locked == true`. Set by `closeDailyClosing()`. No further mutation is permitted until an explicit Reopen.
- **Opening Cash**: The starting cash figure for a day. Either **chained** (`openingCashSource: "chained"`, carried over from the previous locked day's `closingCash`) or **manual** (`openingCashSource: "manual"`, only permitted when there is no previous locked day).
- **Cash Expense**: One line item in a Daily Closing's `expenses[]` array — a real business expense paid out of the physical cash drawer.
- **Cash Deposit**: One line item in a Daily Closing's `deposits[]` array — cash moved out of the drawer into another holding (e.g. Pigmi) that is **not** a business expense.
- **Auto-Posted Transaction**: A `fin_transactions` ledger entry created automatically by `postDailyClosingToLedger()` when a day is closed, tagged `autoPosted: true, autoPostedSource: "daily_closing"`. The mobile app never reads `fin_transactions` directly (see Requirement 3.6) — it only ever sees the *outcome* of this process via `autoPostedTransactionsByEvent` and `postingWarnings` on the `fin_daily_closing` document.
- **Finance Defaults**: `finance_defaults/{eventKey}` documents mapping a business event (e.g. `cash_sales`) to a destination `fin_accounts` document. Read-only from the mobile app's perspective.
- **Identity-Forwarding API Route**: A thin Next.js API route that verifies the caller's Firebase ID token (via Admin SDK `verifyIdToken`), confirms the `financeUser` claim and that the Finance User is still `active`, and then calls an existing `financeClosingService.ts` function using the caller's own `userId`/`userName` — exactly as the admin web routes do today via `getAuthenticatedFirestoreForRequest`, just with Finance User identity instead of Admin identity.
- **Direct-Firestore Read**: A query the mobile app issues straight to Firestore using the Firebase client SDK, authorized purely by Firestore Security Rules (no API route involved).

## Architecture Decision (binding — not open for re-litigation in later phases)

Two things are true simultaneously, and both are required:

1. **Authorization is Firestore Security Rules, not a trusted API layer.** The mobile app signs in with a real Firebase Auth session (via custom token exchange) and reads data straight from Firestore wherever the operation is a simple read or a simple, non-transactional write. A new `isFinanceUser()` rules helper — parallel to the existing `isAdmin()` — governs exactly which collections a Finance User session may touch.
2. **The transactional business logic in `financeClosingService.ts` is never duplicated.** Every mutation that today runs through `runTransaction()` inside that file (add/remove expense, add/remove deposit, update sales, set opening cash, close a day, reopen a day, backfill postings) continues to run through that exact file, unmodified. Firestore Rules cannot express "recompute `cashRevenue` inside a transaction and post N ledger entries," and duplicating that logic in the client would create two sources of truth. So these specific operations are called through **Identity-Forwarding API Routes**: the route verifies the Finance User's ID token server-side (same `verifyIdToken` pattern the web admin routes already use, just checking a different claim), then calls the same service function with the Finance User's identity.

This produces a hybrid, not a compromise:
- **Direct-Firestore, rules-authorized:** viewing Daily Closing history, reading expense categories, reading Finance Defaults (for display only). Posting confirmation is read from the `fin_daily_closing` document's own fields, not from `fin_transactions` (see Requirement 3.6).
- **API-route, identity-forwarded, service-layer-authoritative:** every write that mutates a Daily Closing document (expenses, deposits, sales, opening cash, closingCash/save, reopen).

Firestore Rules still gate the API-route-only collections too (defense in depth) — a Finance User's Firestore session is never granted direct write access to `fin_daily_closing` (see Requirement 3), so even if a future code change accidentally tried a direct client write, Firestore Rules would reject it. The only path that can write `fin_daily_closing`, `fin_transactions`, or `fin_expense_categories.transactionCount` on behalf of a Finance User is the API-route path re-using the untouched service functions.

## Requirements

### Requirement 1: Finance User Authentication Flow

**User Story:** As a Finance User (restaurant manager/cashier), I want to log in with the username and password an admin created for me, so that I can access Daily Closing on my phone without needing a separate admin account.

#### Acceptance Criteria

1. WHEN the Login screen submits a username and password, THE mobile app SHALL call a new `POST /api/mobile/v1/finance/auth/login` route with `{ username, password }` and no Authorization header. All mobile-facing API routes for this feature SHALL live under the `/api/mobile/v1/...` prefix, established from the outset so a future breaking change can be introduced as `/api/mobile/v2/...` without disrupting `v1` clients still in the field — this versioning applies to every mobile route in this document, including those in Requirement 4.
2. WHEN `/api/mobile/v1/finance/auth/login` receives a request, THE route SHALL call the existing, unmodified `authenticateFinanceUser(username, password)` from `services/financeUsersService.ts` using a Firestore instance obtained via the Firebase Admin SDK, and SHALL NOT reimplement credential verification.
3. IF `authenticateFinanceUser` throws (invalid credentials or disabled account), THEN THE route SHALL return HTTP 401 with the thrown message and SHALL NOT mint a custom token.
4. WHEN `authenticateFinanceUser` succeeds, THE route SHALL mint a Firebase Custom Token via the Admin SDK's `createCustomToken(financeUserId, { financeUser: true, active: true })`, where `financeUserId` is the Finance User's `finance_auth` document id used as the Firebase Auth `uid`.
5. WHEN the custom token is minted, THE route SHALL return HTTP 200 with `{ success: true, customToken, user: FinanceUserPublic }` and SHALL NOT include `passwordHash` anywhere in the response (reuse `toFinanceUserPublic`).
6. WHEN the mobile app receives a successful login response, THE mobile app SHALL call `signInWithCustomToken(auth, customToken)` using the Firebase JS/RN client SDK and SHALL treat the resulting Firebase Auth session as the single source of the user's identity for all subsequent Firestore access.
7. IF `signInWithCustomToken` fails after a successful `/login` response (e.g. network drop mid-exchange), THEN THE mobile app SHALL show a retry-capable error and SHALL NOT navigate past the Login screen.
8. WHEN a Finance User session is established, THE mobile app SHALL persist only the Firebase Auth refresh token (managed automatically by the Firebase SDK's persistence layer) and SHALL NOT persist the username or password anywhere on-device.
9. WHERE the platform is iOS or Android, THE mobile app SHALL configure the Firebase Auth SDK to use secure, encrypted on-device persistence (Keychain on iOS, EncryptedSharedPreferences/Keystore-backed storage on Android) for the refresh token — never plain `AsyncStorage`.
10. WHEN the app is relaunched and a valid persisted Firebase Auth session exists, THE mobile app SHALL restore the session automatically (Persistent Login) and SHALL navigate directly to the Home screen, skipping Login.
11. WHEN the user taps Logout, THE mobile app SHALL call Firebase Auth `signOut()`, clear any locally cached Daily Closing draft data for the current device session, and navigate to the Login screen.
12. IF a Finance User's Firestore `active` field is `false` at the time of a fresh login attempt, THEN the existing `authenticateFinanceUser` throw path SHALL surface "This account has been disabled. Contact your administrator." and no custom token SHALL be minted for that attempt.

### Requirement 2: Custom Token Lifecycle, Claim Revocation, and Immediate Session Termination

**User Story:** As an admin, I want disabling or changing a Finance User's password on the web to actually cut off their mobile access immediately, so that offboarding and credential resets are reliable.

#### Acceptance Criteria

1. THE `financeUser` custom claim SHALL be set to `true` only at custom-token-minting time (Requirement 1.4) and SHALL NOT be independently settable by any client.
2. WHEN a Firebase ID token containing `financeUser: true` is presented to Firestore Rules, THE `isFinanceUser()` rule helper SHALL additionally verify `exists(/databases/$(database)/documents/finance_auth/$(request.auth.uid))` AND `get(...).data.active == true` before granting any access — the claim alone SHALL NOT be sufficient.
3. WHEN an admin disables a Finance User (`active: false`) via the existing web Settings > Finance Users page, THE next Firestore request the mobile app makes under that session SHALL be denied by Rules per criterion 2, even though the previously issued custom token/ID token has not expired.
4. WHEN `disableFinanceUser()` is called (admin disabling a Finance User) OR `changeFinancePassword()` is called (admin resetting a Finance User's password), THE implementation SHALL, as part of that same operation, call the Firebase Admin SDK's `revokeRefreshTokens(uid)` for that Finance User's `finance_auth` document id. This is a mandatory part of the authentication architecture, not a deferred enhancement.
5. WHEN `revokeRefreshTokens(uid)` has been called for a Finance User, THE next time the mobile app's Firebase Auth SDK attempts to silently refresh its ID token (which happens automatically, at latest, within the token's remaining lifetime — up to 1 hour), THE refresh SHALL fail, and THE mobile app SHALL treat this exactly as a permission-denied/session-invalid condition per criterion 7 below — administrative disable and password-reset actions SHALL therefore take effect for the mobile session within one token-refresh cycle, not only at next login.
6. THE `disableFinanceUser()` and `changeFinancePassword()` service functions in `services/financeUsersService.ts` SHALL be updated to perform the `revokeRefreshTokens(uid)` call via the Firebase Admin SDK as part of implementing this requirement — this is the one narrow, explicitly-approved exception to the "no modification to existing finance service files" constraint (Requirement 12.7), since immediate revocation cannot be achieved any other way. THE existing signatures, validation, Firestore writes, and audit logging of both functions SHALL remain otherwise unchanged.
7. WHEN the mobile app's Firestore SDK or Firebase Auth SDK reports a permission-denied or token-revoked error on any previously working request, THE mobile app SHALL treat this as "session no longer authorized," sign the user out locally, clear any locally cached Daily Closing draft data for the current device session, and navigate to Login with the message "Your session is no longer valid. Please log in again."
8. THE mobile app SHALL rely on the Firebase Auth SDK's automatic ID token refresh (silent refresh using the persisted refresh token) and SHALL NOT implement its own token refresh logic.

### Requirement 3: Firestore Security Rules — `isFinanceUser()` and Collection Scoping

**User Story:** As the system owner, I want Finance User Firestore access scoped as narrowly as the Daily Closing feature requires, so that a compromised mobile session cannot read or write anything outside Daily Closing.

#### Acceptance Criteria

1. THE `firestore.rules` file SHALL define a new helper function equivalent to:
   ```
   function isFinanceUser() {
     return isSignedIn()
       && request.auth.token.financeUser == true
       && exists(/databases/$(database)/documents/finance_auth/$(request.auth.uid))
       && get(/databases/$(database)/documents/finance_auth/$(request.auth.uid)).data.active == true;
   }
   ```
2. THE `fin_daily_closing/{closingId}` rule SHALL grant `isAdmin()` unchanged full read/write, AND SHALL grant `isFinanceUser()` read access, AND SHALL grant `isFinanceUser()` no direct write access — all Daily Closing mutations for Finance Users flow through the Identity-Forwarding API routes (Requirement 4), never direct client writes, even though the Finance User's own session is what authenticates the API route call.
3. THE `fin_expense_categories/{categoryId}` rule SHALL grant `isFinanceUser()` read-only access (`allow read: if isAdmin() || isFinanceUser();` write remains `isAdmin()`-only).
4. THE `finance_defaults/{eventKey}` rule SHALL grant `isFinanceUser()` read-only access, for the sole purpose of letting the mobile app show which sales/deposit events are and are not yet configured for auto-posting (informational display only — the mobile app never writes this collection and never performs the destination-account resolution itself; that remains inside `postDailyClosingToLedger`).
5. THE `fin_accounts/{accountId}` rule SHALL grant `isFinanceUser()` no access. Rationale: the web Daily Closing screen itself never reads `fin_accounts` directly (account resolution happens server-side inside `postDailyClosingToLedger`), so the mobile app has no legitimate need to read account balances or names, and granting this would leak account balance data to a role narrower than Admin. If a future screen needs it, that is a new requirement, not an oversight.
6. THE `fin_transactions/{transactionId}` rule SHALL grant `isFinanceUser()` no access, direct or scoped. **This permission was considered and deliberately removed** during requirements review: posting status, posting warnings, close status, and `autoPostedTransactionsByEvent` (the event→transactionId map) are already present on the `fin_daily_closing` document itself (Requirement 3.2's read grant), which is sufficient for every UI need identified in Requirement 6 (displaying `postingWarnings`, showing that a day closed successfully). No screen in Requirement 5 requires reading an individual `fin_transactions` document's fields (amount, account names, etc.) directly. If a future screen needs transaction-level detail (e.g. showing the actual posted amount per event), that SHALL be added as a new, separately-justified requirement, not assumed here — the mobile app receives the minimum Firestore permissions necessary for its current, approved screen set.
7. THE `fin_audit_logs/{logId}` rule SHALL grant `isFinanceUser()` no read access (matches "Audit logs" in the explicit non-goals list) — Finance User actions SHALL still be written to this collection (see Requirement 4.9) by the API routes reusing `writeFinanceAuditLog`/`logFinanceAudit`, but the mobile app SHALL NOT be able to read them back.
8. THE following collections SHALL grant `isFinanceUser()` no access whatsoever, with no exceptions: `admins`, `pos_staff`, `pos_open_orders`, `bills`, `fin_transactions`, `fin_accounts`, `fin_expense_subcategories`, `fin_income_categories`, `fin_vendors`, `fin_settings`, `finance_auth` (including the Finance User's own document — self-service profile reads, if ever needed, are a separate future requirement and are explicitly out of scope here), `menus`, `inventory_entries`, `zomato_imports`, and every other existing collection not explicitly listed in criteria 2–4.
9. THE default-deny rule at the bottom of `firestore.rules` (`match /{document=**} { allow read, write: if false; }`) SHALL remain unchanged and SHALL continue to apply to any collection not explicitly matched, including any new collection introduced by a future phase of this feature.
10. WHEN `firestore.rules` is modified for this feature, THE existing `isAdmin()`-gated behavior for every currently-listed collection SHALL remain byte-for-byte unaffected — this feature only ADDS `isFinanceUser()` grants alongside existing `isAdmin()` grants, and never loosens or removes an existing Admin permission.

### Requirement 4: Identity-Forwarding API Routes for Daily Closing Mutations

**User Story:** As a developer, I want every Daily Closing mutation from the mobile app to run through the exact same service functions the web app uses, so that a value produced by the mobile app is indistinguishable from one produced by the web app.

#### Acceptance Criteria

1. THE mobile app SHALL perform every Daily Closing mutation (add/remove expense, add/remove deposit, update sales, set manual opening cash, close/save a day, reopen a day) by calling a new set of versioned API routes under `/api/mobile/v1/finance/closing/...`, mirroring the shape of the existing `/api/finance/closing/...` routes but authenticating the caller as a Finance User instead of an Admin.
2. WHEN a `/api/mobile/v1/finance/closing/...` route receives a request, THE route SHALL verify the `Authorization: Bearer <idToken>` header using the Firebase Admin SDK's `verifyIdToken()`, SHALL reject with HTTP 401 if verification fails or the token lacks `financeUser: true`, and SHALL additionally look up `finance_auth/{uid}` via the Admin SDK and reject with HTTP 403 if the document is missing or `active != true` — mirroring the same defense-in-depth check as the Firestore Rules helper in Requirement 3.1, kept in sync deliberately (both checks must be updated together if the activation model ever changes).
3. WHEN the identity check in criterion 2 passes, THE route SHALL call the existing corresponding function in `services/financeClosingService.ts` (`addDailyClosingExpense`, `removeDailyClosingExpense`, `addDailyClosingDeposit`, `removeDailyClosingDeposit`, `updateDailyClosingSales`, `setDailyClosingOpeningCash`, `closeDailyClosing`) passing the Finance User's `uid` as `userId` and `fullName` as `userName`, with NO modification to those functions' signatures, validation, or internal transaction logic.
4. THE mobile app SHALL NOT call `reopenDailyClosing` or `backfillDailyClosingPostings` — these remain Admin-only, exposed only via the existing web-facing `/api/finance/closing/[date]/reopen` and `/backfill` routes, which continue to require an Admin ID token exactly as today. Reopening a locked day for correction requires contacting an admin; the mobile app's role is Save, not Reopen.
5. IF a mutation route is called for a date whose Daily Closing document has `locked == true`, THEN the underlying service function's existing `assertNotLocked()` check SHALL throw exactly as it does for Admin callers today, and the route SHALL surface that error message with HTTP 400, unchanged from the existing `financeErrorResponse` convention.
6. THE mobile app SHALL treat every response from `/api/mobile/v1/finance/closing/...` identically to how the web app treats `/api/finance/closing/...` responses, plus the additional `serverTime` field from Requirement 10.4: `{ success: true, closing: FinanceDailyClosing, serverTime: string }` on success, `{ success: false, message: string }` with an appropriate status code on failure.
7. THE new mobile API routes SHALL reuse the existing `financeErrorResponse()` helper from `lib/financeApiError.ts` unmodified for error-to-HTTP-status mapping.
8. THE new mobile API routes SHALL NOT use the Firebase Admin SDK to read or write Firestore data directly for any purpose other than (a) verifying the caller's identity per criterion 2, and (b) the one-time custom-token minting in Requirement 1.4 — all Daily Closing data access within these routes SHALL go through the same `services/financeClosingService.ts` functions the web app already calls, using a Firestore client instance obtained the same way the existing `getAuthenticatedFirestoreForRequest` pattern demonstrates (or an equivalent that authenticates as the specific Finance User's own identity, not a privileged service-account bypass).
9. WHEN a mutation succeeds, THE audit trail written by the underlying service function (`writeFinanceAuditLog`) SHALL record the Finance User's `uid` and `fullName` as `userId`/`userName`, exactly as it already records an Admin's `uid`/`email` today — no new audit code path is introduced.
10. EVERY `/api/mobile/v1/finance/closing/...` request body SHALL accept the `deviceTime` field specified in Requirement 10.4, and the route SHALL pass it through unused to any business logic (it is accepted and, at most, logged/stored alongside the mutation's own record for future reconciliation — never passed into any `financeClosingService.ts` function parameter, since none of those functions accept or need a client-supplied timestamp).

### Requirement 5: Screen Inventory

**User Story:** As a Finance User, I want a minimal, focused set of screens so the app does exactly what Daily Closing on the web does — nothing more.

#### Acceptance Criteria

1. THE mobile app SHALL implement exactly these screens: Splash, Login, Home, Daily Closing, History, Settings. There is no separate Profile screen — Finance User identity display and Logout live inside Settings (criterion 9).
2. THE Splash screen SHALL display briefly on cold start while the Firebase Auth SDK determines whether a persisted session exists, then navigate to Home (if authenticated) or Login (if not), per Requirement 1.10.
3. THE Login screen SHALL present Username and Password fields and a Login button, matching Requirement 1's flow, and SHALL show field-level validation for empty username/password before calling the login route.
4. THE Home screen SHALL display: today's date, today's Daily Closing status (Not Started / In Progress / Closed), the resolved Opening Cash for today (chained or manual, per Requirement 6), a "Start Daily Closing" button (shown when today has no document yet or is unlocked with no entries) or "Continue Daily Closing" button (shown when today is unlocked with existing entries), a "History" button, and the connectivity/sync indicator described in Requirement 13.
5. THE Daily Closing screen SHALL implement the workflow in Requirement 6, mirroring the web page's section order exactly: Opening Cash, Cash Expenses, Cash Deposits, Today's Sales, Count the Drawer (Closing Cash), Daily Summary.
6. THE History screen SHALL present a chronological list of previous Daily Closing documents (most recent first), SHALL provide a date picker / date-range selector to narrow the list, and SHALL allow tapping a past day to view it read-only (no edits permitted from History even if that day happens to be unlocked — opening a day for editing is only done from Home's "Continue Daily Closing"). THE History screen SHALL NOT implement free-text search of any kind — date-range filtering is the only supported narrowing mechanism, by deliberate design choice to keep the screen minimal.
7. WHERE a listed day in History is locked, THE mobile app SHALL display its lock status, `closingTime`, and `closedByName` exactly as stored, matching the web Lock Settings page's presentation.
8. THE mobile app SHALL NOT implement: Reports, Transactions ledger browsing of any kind (posting confirmation is derived from the Daily Closing document itself, per Requirement 9.4 — no `fin_transactions` access exists), Accounts management, Finance Defaults management, Finance Users management, Vendors, Dashboard, Audit log browsing, Inventory, POS, or any other admin functionality.
9. THE Settings screen SHALL present, at minimum: the Finance User's `fullName` and `username` (read-only, no editing — those remain Admin-managed via the web Settings > Finance Users page), the app version, a Logout action, a manual "Sync Now" action (Requirement 11), sync status display, and the Diagnostics section described in Requirement 14. THE Settings screen SHALL NOT expose Finance Defaults, Expense Categories, Accounts, Finance Users management, Lock Settings, or Pigmi Settings — those remain exclusively in the web admin app.

### Requirement 6: Daily Closing Workflow and Authoritative Totals

**User Story:** As a Finance User, I want the mobile Daily Closing screen to show me the same totals the web screen would show for the same day, so I can trust the numbers regardless of which client produced them — without the mobile app maintaining its own copy of the finance math.

#### Acceptance Criteria

1. THE mobile app SHALL NOT implement, port, or otherwise reproduce `computeDerivedTotals()`, `roundCurrency()`, `resolveOpeningCash()`, or any other calculation from `services/financeClosingService.ts`. `services/financeClosingService.ts` SHALL remain the single, sole implementation of every Daily Closing formula. There SHALL be exactly one implementation of Daily Closing's business logic in the entire system, web and mobile combined.
2. THE authoritative values for `cashExpenseTotal`, `depositTotal`, `totalCashOut`, `cashRevenue`, and `totalRevenue` SHALL always be the values most recently returned by the server — either from a Direct-Firestore read of `fin_daily_closing/{date}` (Requirement 9) or from the `closing` object returned by a mobile API route mutation response (Requirement 4.6). THE mobile app SHALL treat these server-returned values as the only values that are ever persisted, displayed as final, or relied upon for correctness.
3. WHERE the mobile app is offline and mutations are queued (Requirement 10), THE mobile app MAY display a **local visual preview** of what the totals will likely become once the queued mutations sync, computed by a simple, clearly-labeled, non-authoritative estimate (e.g. summing the queued mutations' own input amounts against the last-known server totals). This preview SHALL be visually distinguished from authoritative, synced totals (e.g. an "estimated" label, a distinct style, or a pending-sync badge on the affected summary rows) and SHALL be discarded/replaced the moment the server's authoritative `closing` object is available — the preview is a UX affordance for responsiveness, never a second source of truth, and its calculation logic (if any) SHALL be simple enough that it is obviously not a reimplementation of `computeDerivedTotals()` (e.g. no rounding-mode replication, no opening-cash chaining logic, no locking logic) — if in doubt, the simpler and less "formula-like" the preview, the better; showing last-known totals with a "pending changes, totals will update after sync" message is an acceptable, even preferable, implementation of this criterion.
4. WHEN `closingCash` is null in the server's returned document, THE mobile app SHALL display `cashRevenue` and `totalRevenue` as unset (`—`), exactly as returned/implied by the server — never computing or displaying `0` in their place.
5. THE mobile app SHALL resolve Opening Cash for a given date by reading the `openingCash`/`openingCashSource` fields already computed and stored server-side by the API route path (Requirement 4) — the mobile app SHALL NOT attempt to independently compute the chained-vs-manual resolution client-side, since that logic (`resolveOpeningCash`, reading the previous day's document) lives inside `financeClosingService.ts` and must not be duplicated.
6. WHEN `openingCashSource == "chained"`, THE Daily Closing screen SHALL display Opening Cash as read-only text (not an editable field), matching the web page's behavior, including the amber "Opening with cash deficit" indicator WHEN `openingCash < 0`.
7. WHEN `openingCashSource == "manual"`, THE Daily Closing screen SHALL display an editable numeric Opening Cash field that calls the `setDailyClosingOpeningCash` mobile API route on blur, matching the web page's `onBlur`-triggered save pattern, and SHALL show the same deficit indicator WHEN the entered value is negative.
8. THE Cash Expenses section SHALL display an "Add Expense" action WHEN the day is unlocked, opening a modal with fields: Category (a picker populated from a Direct-Firestore read of `fin_expense_categories` filtered to `active == true`, matching `activeCategories` in the web page), Amount (numeric), Remarks (optional text). Category and a positive finite Amount SHALL be required before the Save button in that modal is enabled.
9. THE Cash Deposits section SHALL display an "Add Deposit" action WHEN the day is unlocked, opening a modal with fields: Deposit Type (a picker populated from `SUPPORTED_CASH_DEPOSIT_TYPES`/`CASH_DEPOSIT_TYPE_LABELS`, currently just "Pigmi" — reused verbatim from `lib/finance.ts`, not re-declared), Amount (numeric), Remarks (optional text). A positive finite Amount SHALL be required before the Save button in that modal is enabled.
10. WHEN the day is unlocked, EACH expense line and EACH deposit line SHALL show a delete affordance that calls the corresponding `removeDailyClosingExpense`/`removeDailyClosingDeposit` mobile API route after a confirmation prompt, matching the web page's `window.confirm` pattern (adapted to a native confirmation dialog).
11. WHEN the day is locked, THE mobile app SHALL hide all Add/Delete affordances for expenses and deposits, matching the web page's `!locked` conditional rendering.
12. THE Today's Sales section SHALL present four numeric fields — UPI Sales, Zomato Sales, Swiggy Sales, Other Income — each defaulting to the stored value or `0`, each disabled WHEN the day is locked, and each triggering `updateDailyClosingSales` on blur (debounced to on-blur exactly as the web page does, not on every keystroke).
13. THE "Count the Drawer" section SHALL present a single numeric Closing Cash field, disabled WHEN the day is locked, with no default value pre-filled beyond whatever was last saved (matching the web page's `closingCashDraft` starting as an empty string until loaded).
14. THE Daily Summary section SHALL display, in this exact order: Opening Cash, Cash Expenses, Cash Deposits, Total Cash Out, Cash Revenue, UPI Sales, Zomato Sales, Swiggy Sales, Other Income, Total Revenue, Closing Cash — matching the web page's `SummaryRow` sequence, and SHALL be sourced from the server's authoritative document per criterion 2 (with the criterion 3 preview overlay only where mutations are queued).
15. WHEN the day is unlocked, THE Daily Summary section SHALL show a "Save Daily Closing" button that is disabled/blocked WHEN Closing Cash is empty or not a valid number, matching the web page's validation ("Count the cash drawer and enter Closing Cash before saving.").
16. WHEN "Save Daily Closing" is tapped and validation passes, THE mobile app SHALL first ensure the latest sales draft has been persisted (mirroring the web page's `handleSaveSales()` call before the close request), then call the close mobile API route with the entered Closing Cash.
17. WHEN the day is locked, THE Daily Summary section SHALL replace the Save button with a message equivalent to "This day is closed and locked," and SHALL display `closingTime` and `closedByName`, matching the web page.
18. WHEN a Daily Closing document has non-empty `postingWarnings`, THE mobile app SHALL display them exactly as stored (no rewording), in the same position (near the top, above the numbered sections), matching the web page's amber warning panel.

### Requirement 7: Validation Rules

**User Story:** As a Finance User, I want the mobile app to reject the same bad input the web app rejects, so mistakes are caught consistently regardless of which client I use.

#### Acceptance Criteria

1. THE mobile app's Add Expense modal SHALL require a non-empty `categoryId` and SHALL require `amount` to be a finite number greater than 0, matching `addDailyClosingExpense`'s server-side checks (`"Expense category is required."`, `"Amount must be a positive number."`) — client-side validation SHALL mirror, not replace, these server-side checks, and the server-side error SHALL still surface verbatim if a stale client ever bypasses the client check.
2. THE mobile app's Add Deposit modal SHALL require `amount` to be a finite number greater than 0 and a known `type` present in `SUPPORTED_CASH_DEPOSIT_TYPES`, matching `addDailyClosingDeposit`'s checks.
3. THE mobile app SHALL require `closingCash` to be a finite number before enabling "Save Daily Closing," matching `closeDailyClosing`'s check (`"Closing Cash is required."`) and the web page's pre-flight check.
4. THE mobile app SHALL require Opening Cash (when manually editable) to be a finite number, matching `setDailyClosingOpeningCash`'s check (`"Opening Cash must be a valid numeric value."`) — negative values SHALL be permitted (a documented deficit scenario), matching existing behavior.
5. IF any mobile API route call returns `{ success: false, message }`, THEN THE mobile app SHALL display that exact `message` to the user (no client-side re-wording), matching the web app's `readJson()` error-surfacing convention.
6. THE mobile app SHALL disable every input and every Add/Remove/Save affordance on a Daily Closing screen WHEN the loaded document's `locked` field is `true`, with no exceptions — this is both a UX affordance and a defense-in-depth measure, since the authoritative block is still `assertNotLocked()` server-side (Requirement 4.5).
7. THE mobile app's Login screen SHALL require both Username and Password fields to be non-empty before enabling the Login button, and SHALL NOT perform any client-side password strength or format validation beyond non-emptiness (format validation, e.g. username character rules, remains server-side inside `authenticateFinanceUser`/`createFinanceUser`, which the mobile app never duplicates).

### Requirement 8: Locking Behavior

**User Story:** As an admin, I want a day closed from the mobile app to be exactly as immutable as a day closed from the web app, so there is one consistent notion of "locked" regardless of which client closed it.

#### Acceptance Criteria

1. WHEN `closeDailyClosing` is invoked via the mobile API route path (Requirement 4), THE resulting document SHALL have `locked: true`, `closingTime`, `closedBy` (the Finance User's `uid`), and `closedByName` (the Finance User's `fullName`) set exactly as `closeDailyClosing` already does for Admin callers — no new fields, no different semantics.
2. THE mobile app SHALL NOT expose any Reopen affordance. Reopening a locked day remains an Admin-only action performed via the existing web app, per Requirement 4.4.
3. IF a day is reopened by an admin on the web WHILE a Finance User has that day's Daily Closing screen open on their device, THEN the next mobile mutation attempt against that day SHALL succeed normally (the document is unlocked again), and the next Direct-Firestore read of that document SHALL reflect `locked: false` — no special client-side handling is required beyond re-reading current state, since Firestore's real-time listener (or a manual refresh) will surface the change.
4. IF a day is closed by an admin on the web WHILE a Finance User has unsynced local changes queued for that same day (see Requirement 10), THEN the queued mutations SHALL fail with the server-side "already closed and locked" error when they attempt to replay (Requirement 11.5), and the mobile app SHALL surface this as a conflict requiring the user to discard the queued changes — the mobile app SHALL NOT retry a mutation that failed due to a lock conflict.
5. THE Firestore Rules change in Requirement 3.2 (no direct Finance User write to `fin_daily_closing`) SHALL, as a side effect, make it structurally impossible for a Finance User session to ever write to a locked (or unlocked) Daily Closing document except through the API route path — this is intentional defense in depth, not a gap to be "fixed" by granting direct write access later.

### Requirement 9: Direct-Firestore Read Paths

**User Story:** As a Finance User, I want the app to load quickly and stay responsive, so simple lookups shouldn't need a network round-trip through a custom API when Firestore can serve them directly and securely.

#### Acceptance Criteria

1. THE mobile app SHALL read `fin_daily_closing/{date}` documents directly via the Firebase client SDK for display purposes (Home screen status, History screen listing, viewing a locked day) — authorized by the Requirement 3.2 read grant — and SHALL only use the API route path when actually mutating a document.
2. THE mobile app SHALL read `fin_expense_categories` directly via the Firebase client SDK, filtered to `branchId == "main"` (the existing `DEFAULT_BRANCH_ID`) and `active == true`, matching the query shape already used by `getExpenseCategories()`.
3. THE mobile app SHALL read `finance_defaults` directly via the Firebase client SDK for the sole purpose of informationally cross-referencing `postingWarnings` event names against configured mappings if the UI chooses to show "configure this in Finance Defaults" hints — this is optional UI polish, not required for the core Save flow, since `postingWarnings` strings are already human-readable and pre-composed server-side.
4. THE mobile app SHALL NOT read `fin_transactions` under any circumstance, direct or otherwise — per Requirement 3.6, this permission was evaluated and removed as unnecessary. Confirmation that a day's sales/deposits posted successfully SHALL be derived entirely from the `fin_daily_closing` document's own `autoPostedTransactionsByEvent` (which events posted) and `postingWarnings` (which did not, and why) fields, both already returned by every mobile API route response and readable directly per Requirement 9.1.
5. THE mobile app SHALL NOT cache or read any collection not explicitly listed in Requirement 3 as readable by `isFinanceUser()`.
6. History screen date-range queries SHALL use the same `branchId` + `date >=` + `date <=` query shape as `getDailyClosingsForRange()`, ensuring any Firestore composite index required is the same index the web app's equivalent query already needs (see Requirement 12.6 for index deployment).

### Requirement 10: Offline Strategy

**User Story:** As a Finance User closing the register at the end of a busy night, I want to keep working even if the venue's internet is briefly down, so I never lose the numbers I've already entered.

#### Acceptance Criteria

1. WHILE the device has no network connectivity, THE mobile app SHALL allow continuing to add/remove expense and deposit line items, edit the sales draft fields, and edit the Closing Cash field for the CURRENT unlocked day only — using locally cached copies of the day's most recently known server state as the working baseline.
2. THE mobile app SHALL NOT allow starting to edit a day other than today while offline if that day's document has never been fetched successfully at least once during the current app session — there is no legitimate "guess" at another day's state to edit against.
3. EACH offline mutation (add expense, remove expense, add deposit, remove deposit, update sales, set opening cash, save/close) SHALL be recorded in a local queue with: a generated idempotency key, the operation type, its input payload, the target date, a client-side timestamp, a `deviceId` (a stable per-installation identifier), a `clientVersion` (the mobile app's version string), a `retryCount` (initialized to 0, incremented on each replay attempt), and a `createdOffline` boolean (`true` if the mutation was created while the device was detected offline, `false` if it was queued for some other reason, e.g. Requirement 11.5's "stop replaying" behavior) — before any attempt to replay it against the server. THE `deviceId`, `clientVersion`, `retryCount`, and `createdOffline` fields are for diagnostics and future support purposes only (see Requirement 14) and SHALL NOT influence synchronization order, retry logic, or conflict resolution in any way beyond what is already specified in Requirement 11.
4. EVERY mutation request sent to a `/api/mobile/v1/finance/...` route — whether sent immediately (online) or replayed from the queue (Requirement 11) — SHALL include a `deviceTime` field (the client's own clock timestamp at the moment of the request) in its request payload. EVERY successful response from such a route SHALL include a `serverTime` field (the server's own clock timestamp at the moment of the response) in its response payload. Both fields are for future reconciliation and troubleshooting purposes only (e.g. diagnosing clock drift or investigating a disputed close time) and SHALL NOT be used as an authoritative input to any Daily Closing formula, locking decision, or idempotency check — those continue to rely exclusively on server-side logic and timestamps exactly as `financeClosingService.ts` already generates them (e.g. `toTimeKey()`, `serverTimestamp()`).
5. WHILE queued mutations exist that have not yet synced, THE mobile app SHALL display each affected line item / field with a "Pending Sync" indicator, and THE Daily Closing screen for that date SHALL display an overall "Pending Sync" banner.
6. THE mobile app SHALL show a non-authoritative local preview reflecting queued mutations against the day's totals, per Requirement 6.3 — this preview SHALL be visually distinguished from authoritative totals and SHALL NOT be produced by reimplementing `computeDerivedTotals()` or any other server-side formula; a simple "pending changes, totals will update after sync" treatment satisfies this criterion.
7. THE mobile app SHALL NOT allow queuing a "Save Daily Closing" (close) mutation for a day that already has other queued, unsynced mutations ahead of it in the queue for that same date — close SHALL always be the last queued operation for a given date, enforced client-side before it is even added to the queue.
8. THE mobile app SHALL detect network state transitions (offline → online) using a standard connectivity-detection library and SHALL NOT rely solely on request failures to infer offline state.
9. WHILE offline, THE mobile app SHALL display a persistent, unobtrusive offline banner distinct from the per-mutation "Pending Sync" indicators, and SHALL distinguish a detected "slow network" condition (requests taking unusually long) from a fully offline condition, showing an appropriate banner for each.
10. THE mobile app SHALL never lose a queued mutation due to an app kill or crash — the queue SHALL be persisted to on-device storage (not memory-only) immediately when a mutation is added, before any network attempt.

### Requirement 11: Synchronization Strategy

**User Story:** As a Finance User, I want my offline changes to apply automatically and safely once I'm back online, without ever double-counting an expense or double-posting to the ledger.

#### Acceptance Criteria

1. WHEN connectivity is restored (per Requirement 10.8's detection), THE mobile app SHALL begin replaying the local mutation queue automatically, in strict FIFO order per date, within 5 seconds of the connectivity-restored event.
2. EACH replayed mutation SHALL be sent to its corresponding mobile API route exactly once per attempt, and THE mobile app SHALL wait for that attempt's response before sending the next queued mutation for the same date (mutations for different dates MAY be replayed concurrently, since they touch independent documents).
3. WHEN a replayed mutation succeeds, THE mobile app SHALL remove it from the local queue and SHALL update the local cached view of that day's document with the server's authoritative returned `closing` object (replacing, not merging with, the non-authoritative local preview from Requirement 10.6).
4. IF a replayed "add expense" or "add deposit" mutation is retried after an ambiguous prior failure (e.g. a request timeout where the server may or may not have applied it), THEN THE mobile app SHALL rely on the idempotency key from Requirement 10.3 being surfaced to the corresponding mobile API route, and THE mobile API route SHALL be responsible for de-duplicating based on that key before calling the underlying service function — **this requires the mobile API routes to persist a short-lived idempotency record** (e.g. a dedicated `fin_mobile_idempotency/{key}` document or equivalent) so retried network calls cannot cause the same expense/deposit to be recorded twice; this is a new, narrowly-scoped piece of infrastructure the mobile feature must add, and it does not touch or duplicate any logic inside `financeClosingService.ts` itself (the idempotency check happens before that service is called).
5. IF a replayed mutation fails because the target day is now locked (Requirement 8.4) or because of any other server-rejected validation (Requirement 7), THEN THE mobile app SHALL stop replaying further queued mutations for that specific date (but SHALL continue replaying other dates' queues), mark the failed mutation and every mutation queued after it for that date as "Sync Failed," and present the user a choice to Retry (re-attempt) or Discard (drop the failed mutation and everything queued after it for that date, since later mutations may depend on it).
6. WHEN a queued mutation has failed and been retried 3 times without success (excluding lock-conflict failures, which never auto-retry per criterion 5), THE mobile app SHALL stop auto-retrying that mutation, mark it "Sync Failed," and require explicit user action (manual Retry from Settings' "Sync Now" or from the affected Daily Closing screen) rather than continuing to retry silently in the background.
7. THE mobile app SHALL show, per date with pending or failed items, one of the four states defined in Requirement 13.1 (**🟢 Synced**, **🟡 Pending Sync**, **🔴 Offline**, **🔴 Sync Failed**), with a **Retry** action available whenever the state is Sync Failed.
8. THE Settings screen's "Sync Now" action (Requirement 5.9) SHALL manually trigger the same replay logic as automatic connectivity-restoration, for use when a user wants to force a sync attempt without waiting for automatic detection.
9. IN ADDITION to triggering on connectivity restoration (criterion 1) and manual "Sync Now" (criterion 8), THE mobile app SHALL automatically trigger the same replay logic whenever the application transitions from the background to the active foreground state (i.e. on every React Native `AppState` change to `"active"`), so a Finance User who backgrounds the app (e.g. to answer a call) and returns gets an automatic sync attempt without needing to notice and tap "Sync Now" themselves. This trigger SHALL be subject to the same FIFO-per-date, retry-limit, and lock-conflict rules as every other sync trigger — it is an additional trigger for the same replay engine, not a different synchronization mechanism.
10. WHEN all queued mutations for a date have synced successfully, THE mobile app SHALL clear that date's "Pending Sync" banner and idempotency records for mutations older than 24 hours SHALL be eligible for server-side cleanup (implementation detail left to design phase; the requirement is only that idempotency records are not retained indefinitely).

### Requirement 12: Setup and Deployment Requirements

**User Story:** As the project owner, I want to know exactly what new infrastructure and secrets this feature requires before implementation starts, so I can provision them safely.

#### Acceptance Criteria

1. THE implementation SHALL require adding `firebase-admin` as a new dependency to the Next.js project (`package.json`), used exclusively by the two API route families in Requirements 1 and 4.
2. THE implementation SHALL require a Firebase service account credential (JSON key or equivalent Application Default Credentials setup) to initialize the Admin SDK. **This is a security-sensitive secret** — it SHALL be stored via environment variables / the deployment platform's secret manager, SHALL NOT be committed to the repository, and SHALL NOT be logged. The user (project owner) must provision this credential themselves via the Firebase Console (Project Settings > Service Accounts).
3. THE implementation SHALL require enabling Custom Token minting and Custom Claims on the existing Firebase project — no separate Firebase project or additional Firebase product (e.g. no Cloud Functions requirement, since the identity-forwarding routes run as ordinary Next.js API routes on the existing hosting).
4. THE implementation SHALL require deploying the updated `firestore.rules` (Requirement 3) via the existing `firebase deploy --only firestore:rules` workflow already used for this project (per `firebase.json`).
5. THE implementation SHALL require a new Firestore collection for mutation idempotency tracking (Requirement 11.4) with an appropriate TTL/cleanup policy — this is a new, minimal collection, not a modification to any existing collection's schema.
6. THE implementation SHALL require reviewing `firestore.indexes.json` for the History screen's date-range query (Requirement 9.6); if an equivalent composite index does not already exist for the web app's analogous `getDailyClosingsForRange()` query, a new index SHALL be added and deployed via `firebase deploy --only firestore:indexes`.
7. THE implementation SHALL require no changes to any existing Firestore document schema, no changes to `financeClosingService.ts`, `financeCategoriesService.ts`, `financeDefaultsService.ts`, `financeAccountsService.ts`, `financeTransactionsService.ts`, or `financeAuditService.ts` — every acceptance criterion above is satisfied by additive changes only (new rules grants, new API routes, new mobile client), consistent with the "port, don't rewrite" mandate. THE ONE EXPLICIT EXCEPTION is `services/financeUsersService.ts`, which SHALL gain a `revokeRefreshTokens(uid)` Admin SDK call inside `disableFinanceUser()` and `changeFinancePassword()` per Requirement 2.4-2.6 — no other function in that file, and no other finance service file, SHALL be modified.
8. THE implementation SHALL require standard React Native tooling setup (Android Studio / Xcode toolchains, a bundle identifier and package name to be chosen by the project owner, app icons and splash assets) — these are conventional mobile app build prerequisites, not Firebase-specific, and are called out here only so they are not overlooked during environment setup.

### Requirement 13: Connectivity and Sync State Indicator on Home

**User Story:** As a restaurant manager, I want to glance at the Home screen and immediately know whether today's numbers are actually saved to the server, so I never assume something synced when it didn't.

#### Acceptance Criteria

1. THE Home screen SHALL always display a connectivity/sync indicator showing exactly one of four distinct states, never merging any two of them: **🟢 Synced** (connected, no pending mutations, last sync succeeded), **🟡 Pending Sync** (at least one queued mutation is awaiting or currently attempting sync, and no mutation for the affected date has definitively failed), **🔴 Offline** (no network connectivity detected, per Requirement 10.8's detection mechanism — regardless of whether any mutations happen to be queued), and **🔴 Sync Failed** (network connectivity is present, but at least one queued mutation has exhausted its automatic retries per Requirement 11.6 and requires manual intervention). Offline and Sync Failed SHALL always be presented as two distinct, separately labeled states, never collapsed into one "problem" state, since they require different user actions (wait for connectivity vs. manually retry/discard).
2. THE indicator's state SHALL be derived from the same connectivity-detection mechanism as Requirement 10.8 and the same queue state as Requirement 11.7 — it SHALL NOT introduce a separate, independent notion of connectivity. Precedence when multiple conditions could apply simultaneously: Offline takes precedence over Pending Sync (if there's no connectivity, nothing can be "in progress"); Sync Failed takes precedence over Pending Sync when both a failed and a still-pending item exist, since the failed item requires attention first.
3. WHEN the indicator shows "🔴 Sync Failed", tapping the indicator SHALL navigate to Settings' sync status detail (Requirement 11.8, Requirement 14).
4. THE indicator SHALL update in real time as connectivity and queue state change, without requiring the user to manually refresh the Home screen.

### Requirement 14: Diagnostics Section (Settings)

**User Story:** As a Finance User or a support person helping them, I want a small diagnostics panel so problems can be triaged without needing developer tools.

#### Acceptance Criteria

1. THE Settings screen SHALL include a Diagnostics section displaying, at minimum: the current Finance User's `fullName`/`username` ("Current User"), the app version ("App Version"), the native build number ("Build Number"), the build environment ("Environment": Development / Staging / Production), the configured Firebase project id ("Firebase Project"), the mobile API version this build targets ("API Version", e.g. `v1`, matching the `/api/mobile/v1/...` prefix from Requirement 4.1/1.1), the timestamp of the last successful sync ("Last Successful Sync"), the current overall sync status using the four-state vocabulary from Requirement 13.1 ("Current Sync Status"), the number of mutations currently in the local queue ("Queue Size"), a breakdown of how many of those are awaiting their first/next attempt ("Pending Operations"), and how many have exhausted retries and require manual action ("Failed Operations").
2. THE Diagnostics section SHALL be read-only and informational — it SHALL NOT expose any action beyond what already exists elsewhere (Logout, Sync Now, and the per-item Retry/Discard actions already specified in the Sync section of Settings per Requirement 5.9), and SHALL NOT expose raw Firestore data, tokens, or credentials of any kind.
3. THE Diagnostics section's purpose is strictly troubleshooting and future support; it SHALL NOT be used as a substitute for the per-mutation Pending Sync / Sync Failed indicators specified in Requirement 11 — those remain scoped to the Daily Closing screen and Home indicator, while Diagnostics provides an app-wide summary view.

### Requirement 15: Extensible Application Architecture (Finance Mobile Application, Not "Daily Closing App")

**User Story:** As the project owner, I want this app built as the foundation for a broader Finance Mobile Application, so that adding future modules (Inventory Count, Purchase Entry, Attendance, Kitchen, Expense Entry) never requires restructuring what's already shipped.

#### Acceptance Criteria

1. THE mobile application SHALL be named, structured, and packaged as a general **Finance Mobile Application**, not as a single-purpose "Daily Closing App" — this applies to the project/app naming, the root navigation structure, and the folder structure (detailed in design.md), not to any user-facing rebranding beyond what's natural (the app may still prominently feature Daily Closing as its only current capability).
2. THE navigation structure SHALL be organized so that Daily Closing is one module among potentially several, rather than being hard-coded as the app's only possible screen graph — e.g. a module-based navigation structure (a Home/dashboard screen that could list multiple module entry points, even though only one entry point exists today) rather than a flat, Daily-Closing-specific screen stack that would need to be torn up to add a second module.
3. THE authentication, offline-queue, and synchronization infrastructure (Requirements 1–2, 10–11) SHALL be designed generically enough (e.g. a generic queued-mutation shape, a generic identity-forwarding API route pattern) that a future module could reuse the same mechanisms without requiring a rewrite of this feature's infrastructure — this is a design-quality expectation for design.md to satisfy, not a claim that this requirements document specifies any future module's behavior.
4. THE mobile app SHALL implement ONLY the Daily Closing module in this phase. Inventory Count, Purchase Entry, Attendance, Kitchen, Expense Entry, and any other future module SHALL NOT be implemented, stubbed with placeholder screens, or referenced in navigation as available — "extensible" means the architecture does not obstruct future addition, not that placeholder UI for unbuilt modules should exist today.

### Requirement 16: Single-Branch Scope

**User Story:** As the project owner, I want the mobile app to match the web app's current single-branch reality, so this feature doesn't introduce speculative multi-tenancy complexity the finance system itself doesn't have yet.

#### Acceptance Criteria

1. THE mobile app SHALL operate against exactly one branch, using the existing `DEFAULT_BRANCH_ID` (`"main"`) constant from `lib/finance.ts` wherever a `branchId` filter is required (Requirement 9.2, 9.6, and any Firestore query issued by the mobile app or its API routes) — matching the web app's current behavior exactly.
2. THE mobile app SHALL NOT implement any branch-selection UI, branch-switching mechanism, or per-branch configuration of any kind. There is exactly one branch, hard-coded to the same constant the web app already uses, imported/referenced rather than re-declared.
3. THE mobile app's data models, API routes, and Firestore Rules SHALL NOT introduce any multi-branch abstraction (e.g. no "current branch" state, no branch-scoped session data) beyond passing through the existing `branchId` field already present on every relevant document — this is a deliberate scope limitation, not an oversight, and mirrors the web application's own current single-branch limitation. Multi-branch support, if ever needed, SHALL be designed only once the underlying finance system itself becomes multi-branch, and is explicitly out of scope for this feature.

### Requirement 17: Local Error Logging

**User Story:** As a developer or support person, I want unexpected runtime errors captured locally on the device, so a Finance User experiencing a bug can have it diagnosed after the fact without needing a remote crash-reporting service.

#### Acceptance Criteria

1. WHEN the mobile app encounters an unexpected runtime error (an unhandled exception caught by the top-level error boundary, a rejected promise surfaced to a global handler, or an explicit `catch` block that represents an unexpected/unrecoverable condition rather than a normal validation failure), THE mobile app SHALL record a local log entry containing, at minimum: a `timestamp`, the `screen` (route name) active when the error occurred, the `operation` being attempted (if identifiable, e.g. the mutation or query name; `null`/omitted if not applicable), the `error message`, and the `stack trace` when available.
2. THE mobile app SHALL persist these log entries on-device (e.g. via MMKV, following the same non-sensitive-storage convention as the offline queue) so they survive app restarts, and SHALL bound the log's retained size/age (e.g. a maximum entry count or age, oldest entries evicted first) so it cannot grow unbounded.
3. THE mobile app SHALL NOT transmit these log entries to any remote service, crash-reporting platform, or analytics provider as part of this feature — this is explicitly local-only, on-device diagnostic infrastructure. Remote crash reporting, if ever desired, is a separate future feature requiring its own privacy/data-handling consideration, not an implicit extension of this requirement.
4. THE mobile app SHALL NOT log any Finance User credential (username, password), any Firebase Auth token, or any raw Firestore document content beyond what is already visible in the error message/stack trace itself — this is a data-minimization constraint on the logger, not a demand that errors be scrubbed of all context.
5. THE Settings/Diagnostics area MAY expose a way to view or export these local logs for support purposes (e.g. "Copy diagnostic logs" or "View error log") — this is a reasonable extension of Requirement 14's Diagnostics section but is not itself mandatory; recording the logs (criteria 1-4) is mandatory, a dedicated viewer UI is a nice-to-have left to design.md/implementation to decide.

## Non-Goals (Explicit)

The following are out of scope for this feature and SHALL NOT be implemented as part of it:
- Reports, Dashboard, Transactions ledger browsing of any kind (no `fin_transactions` access exists at all — see Requirement 3.6), Accounts management, Finance Defaults management (write side), Finance Users management, Vendors, Audit log browsing, Inventory, POS, or any other admin functionality.
- Reopening a locked day from the mobile app (Admin-only, web-only).
- Backfilling missing auto-postings from the mobile app (Admin-only, web-only).
- Any modification to `financeClosingService.ts` or any other existing finance service file, EXCEPT the single narrowly-scoped `revokeRefreshTokens()` addition to `financeUsersService.ts` (Requirement 2.4-2.6).
- Any new Firestore collection for Daily Closing data itself — only the narrowly-scoped idempotency-tracking collection (Requirement 12.5) is new.
- A separate Profile screen — Finance User identity display and Logout are part of Settings (Requirement 5).
- Self-service Finance User profile editing (name/username/password) from the mobile app.
- Free-text or full-text search over Daily Closing content in History (chronological list + date-range filtering only).
- Any future Finance Mobile Application module (Inventory Count, Purchase Entry, Attendance, Kitchen, Expense Entry) — including placeholder screens, navigation entries, or stub code for them (Requirement 15.4).
- Porting, re-implementing, or otherwise duplicating `computeDerivedTotals()`, `roundCurrency()`, `resolveOpeningCash()`, or any other Daily Closing formula into the mobile client (Requirement 6.1) — the mobile app displays server-authoritative totals and, at most, a clearly-non-authoritative offline preview (Requirement 6.3).
- Multi-branch support of any kind — branch selection, branch switching, or per-branch configuration (Requirement 16). The mobile app is single-branch, matching the web app's current scope exactly.
- Remote crash reporting or analytics transmission of local error logs (Requirement 17.3) — logging is local/on-device only at this stage.
